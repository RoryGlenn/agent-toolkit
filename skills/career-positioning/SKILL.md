# Career Positioning

Make the user's relevant work easy for a recruiter or hiring manager to understand and verify.

## Preserve the positioning contract

For Rory, keep full-stack software engineering as the primary identity, with backend, automation, and AI/agentic systems as complementary strengths unless he explicitly changes that direction. Interest in AI does not imply giving up React, frontend work, full-stack titles, or broader engineering opportunities. Current user steering takes precedence over this baseline.

Resolve the requested surfaces and goals from the conversation and existing profile. Keep genuine employment titles distinct from a descriptive headline. Do not promise a particular wording will maximize recruiter volume; explain which relevant role families it makes visible.

## Build from evidence

- Inspect the current profile and the most relevant resume or project sources. Record enough provenance to distinguish user-supplied facts, current public source, verified behavior, and unverified claims.
- Surface conflicting dates, titles, or credentials. Continue independent improvements, but leave the disputed fields unchanged until resolved. An old resume is not automatically authoritative over the current profile.
- Select a few concrete accomplishments. Preserve the scope and attribution of numbers: test coverage is not an AI-productivity measure unless the causal connection is established.
- Distinguish a model host, an instruction/skill package, deterministic workflow code, and a standalone model-backed application. Explain what the user actually built.
- Keep package tests, fixture-based behavior checks, live integrations, live model evaluations, and real-user outcomes separate. A demonstration replay is not a performance benchmark. Do not infer production adoption, model accuracy, cost savings, or reliability from static source or mocked tests.

## Shape the profile and proof

Lead with the role identity and what the user builds. Use technical keywords supported by evidence; make the About section readable prose rather than a duplicate resume or exhaustive skill inventory. Retain the user's voice and uncertainty where it matters.

Choose featured skills that balance the core role with the desired specialty. Retain supported core skills, such as Python, TypeScript, React, and full-stack development, alongside a demonstrated agentic skill. Include a named technology only when the current evidence supports it; this example is not a required list. Keep other supported skills in the broader list.

Feature existing relevant projects before proposing new ones. A concise case study should explain the problem, design decisions, the user's contribution, observed results, and limits. A useful demo shows a task, operations, verification, and a failure/recovery path when supported. Provide reproduction steps and exact source/version; label fixture inputs and editorial replay timing. Reuse available document or PDF skills for requested artifacts.

Keep public portfolio material separate from workplace code, credentials, private media, and third-party data. Use public or deliberately fictional examples for public demonstrations.

## Apply and verify requested changes

Advice or review alone does not publish a profile change. An explicit request to update the profile, or approval of a proposed update, authorizes routine evidence-supported edits within that scope; no second approval is needed for the same work. Preserve unrelated profile fields and existing visibility preferences. Do not create new automations, services, or broad posting campaigns as part of a profile edit.

For browser editing, follow the current tool documentation. Inspect current values before editing. Rich-text replacement can append accidentally: verify the exact replacement before saving, and inspect visible paragraph spacing afterward. Keep only one writer on a given profile section; do not overwrite an edit owned by another active session.

A prepared editor, successful click, generated artifact, or upload attempt is not a published result. Reopen or reload the target and verify the saved text, links, placement, and relevant settings. Report only observed completion.

If access fails, perform a bounded documented recovery. If the same failure persists, preserve the proposed copy, last verified state, uncertain save attempts, and remaining sections in the existing task workspace or conversation. Continue independent preparation and identify the smallest user-only recovery action without claiming its success is guaranteed. Re-read live state before resuming; do not repeat a possibly completed mutation blindly.
