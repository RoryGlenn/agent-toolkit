# Chapter 12. Stream Processing

Original applied guidance, not copied book text. These procedures are engineering deductions; retrieve the cited source sections before attributing a consequential claim to DDIA. Verify product/version guarantees independently.

## Source orientation

- Unbounded input changes completion, sorting, state retention, and recovery assumptions. Choose messaging by loss tolerance, consumer speed, durability, ordering, replay, and backpressure needs.
- Queues distribute individual messages and may reorder them during redelivery; log partitions preserve order only within a partition and normally couple its processing to one consumer. Consumer progress is separate from retained history, and lag beyond retention loses replayability.
- Dual writes can diverge even without a failure when concurrent writes are ordered differently. CDC derives other representations from a source order. Bootstrap needs a consistent snapshot tied to a known log position.
- CDC exposes database schemas as contracts. A transactional outbox can decouple internal and external schemas while committing the domain update and outbox record together; it adds write and transformation costs.
- Event sourcing and CDC have different abstraction and replay requirements. Log compaction is appropriate when newer records fully supersede older values, but not generally for intent events or historical dimension versions. Immutability must accommodate real deletion and retention requirements.
- Event time differs from processing time; late-event policy, windows, clock trust, join-time semantics, and state size must be explicit. Replaying a join against current mutable data can change historical results.
- Checkpointing and internal stream transactions cover their defined boundary, not arbitrary external effects. Idempotence may require atomic effect+offset/ID storage, deterministic ordered replay, and fencing of former processors.

## Queues, logs, retention and backpressure

Concept: `stream-delivery`.

**Apply when:** Select messaging or reason about consumer lag and replay.

**Procedure:** Specify per-key ordering, fan-out versus competing consumers, acknowledgement and redelivery, retention and lag limits. Separate offset persistence from effects; calculate whether a slow consumer can catch up before history expires.

**Qualifications:** Log ordering is commonly per partition, not universal. Retained bytes and offsets do not guarantee every downstream effect is recoverable.

**Incorrect example:** Assume a queue can replay all prior events, or ignore a consumer falling behind retention.

**Sufficient example:** Choose queue/log behavior from recovery needs and monitor recoverable lag with a deliberate response.

**Falsification check:** Pause a consumer across retention boundaries and test restart behavior plus missing-history detection.

**Source sections:** `OEBPS/ch12.html#sec_stream_logs_vs_messaging`, `OEBPS/ch12.html#sec_stream_log_offsets`, `OEBPS/ch12.html#sec_stream_disk_usage`.

## CDC, outbox and snapshot-log handoff

Concept: `cdc-handoff`.

**Apply when:** Keep a derived system synchronized with a transactional database.

**Procedure:** Trace commit order and atomic publication of change intent. Define snapshot boundary, subsequent log position, duplicate handling and schema coupling. Compare native CDC, transactional outbox or a simpler same-database view based on the actual need.

**Qualifications:** Reversing two independent writes does not make a dual write atomic. Outbox publication still requires idempotent/reconcilable consumers and operation ownership.

**Incorrect example:** Write database then index directly and assume retries prevent every lost or reordered change.

**Sufficient example:** Capture committed change intent atomically, process ordered/versioned updates and provide rebuild/reconciliation.

**Falsification check:** Crash at every handoff and update during snapshot; compare final projection to authoritative state.

**Source sections:** `OEBPS/ch12.html#sec_stream_sync`, `OEBPS/ch12.html#sec_stream_cdc`, `OEBPS/ch12.html#sec_stream_cdc_snapshot`.

## Events, CDC, compaction and immutability

Concept: `stream-history`.

**Apply when:** Choose retained history or rebuild a projection.

**Procedure:** Distinguish domain events from state changes and latest-value compaction. Identify required historical values, schema/code versions, deletion obligations and rebuild horizon. Define whether replay targets fresh state or existing effects.

**Qualifications:** Latest-state compaction loses prior versions needed for historical enrichment. Immutable histories still need privacy and correction policies.

**Incorrect example:** Rebuild historical invoices using a compacted table containing only current tax rates.

**Sufficient example:** Retain appropriate versioned reference inputs or authoritative historical outcomes and define deletion handling.

**Falsification check:** Change reference data, replay old events and verify historical business results remain as intended.

**Source sections:** `OEBPS/ch12.html#sec_stream_event_sourcing`, `OEBPS/ch12.html#sec_stream_log_compaction`, `OEBPS/ch12.html#sec_stream_immutability_limitations`.

## Event time, windows and temporal joins

Concept: `stream-time-joins`.

**Apply when:** Aggregate by event time or enrich/join streams.

**Procedure:** Define source clock trust, event versus processing time, window type, watermark/late policy and correction behavior. For stream-stream, stream-table and table-table joins specify retained state and historical versus current lookup semantics.

Specify window membership and close/correction policy before selecting engine settings:

| Window | Membership decision | Failure case to test |
| --- | --- | --- |
| Tumbling | Fixed non-overlapping intervals, such as event-time calendar days. | An event arriving tomorrow whose event time belongs to yesterday. |
| Hopping | Fixed-duration windows started at a smaller repeated interval; events can belong to several. | A boundary event duplicated across legitimate windows versus accidental duplicate input. |
| Sliding | A moving/event-relative interval whose exact trigger semantics depend on the engine. | Closely spaced events around eviction, with delayed/out-of-order arrival. |
| Session | Activity grouped until a configured inactivity gap. | A late bridging event that merges sessions previously emitted separately. |

Choose permitted lateness from a stated clock/delivery assumption and business cost. Define
whether a late result is corrected, separately reported or rejected. Measure retained state
and cleanup; unbounded lateness cannot be paired with a finite retention promise for free.

| Join | State and semantics to establish | Falsification history |
| --- | --- | --- |
| Stream-stream | Both sides retained over the allowed matching interval and lateness; output cardinality defined. | Matching partner arrives after one side was evicted. |
| Stream-table | Current lookup versus event-time historical enrichment is explicit. | A tax/profile change occurs between original processing and replay. |
| Table-table | Updates and deletes on either side update the materialized relation. | Change a dimension, then delete a fact while notifications reorder. |

The same event can produce different enrichment under current-value lookup at a later time;
that can be intentional for a current-state view but is wrong for a historical invariant.
Keep necessary reference versions or store authoritative historical outcomes. Compaction to
latest values alone cannot reconstruct every historical join.

**Qualifications:** Watermarks reflect assumptions, not proof that no late event exists. Latest enrichment state can make replay nondeterministic.

**Incorrect example:** Close daily revenue on processing midnight and silently discard delayed transactions from offline clients.

**Sufficient example:** Use an explicit lateness/correction policy and versioned enrichment where historical meaning is required.

**Falsification check:** Reorder and delay events across window boundaries, change dimensions, then replay and compare specified outputs.

**Source sections:** `OEBPS/ch12.html#sec_stream_time`, `OEBPS/ch12.html#id344`, `OEBPS/ch12.html#sec_stream_table_joins`, `OEBPS/ch12.html#sec_stream_join_time`, `OEBPS/ch12.html#id444`, `OEBPS/ch12.html#id346`.

## Checkpoints, effects and state recovery

Concept: `stream-recovery`.

**Apply when:** Claim exactly-once stream processing or recover stateful consumers.

**Procedure:** Trace atomicity between consumed position, local state and each output. Include sink semantics, ownership fencing, checkpoint completeness and replay identities. Separate framework-internal guarantees from external side effects.

Match the processing use case to its state and output obligations: complex-event patterns
need defined order and timeout; analytics/windows need bounded aggregation and corrections;
incremental materialized views must propagate inserts, updates and deletes; standing search
queries must preserve authorization and deletion semantics. Rebuilding each from an event log
requires sufficient retained history, transformation version and compatible enrichment inputs.

**Qualifications:** A checkpoint does not atomically commit an arbitrary external API call. Recovery requires both retained input and compatible state/code.

**Incorrect example:** Commit input offsets before durable effects, then skip those events after a crash.

**Sufficient example:** Commit compatible state/effects/positions together where supported or use durable identity/reconciliation at each boundary.

**Falsification check:** Crash on each side of checkpoint/effect commits, restore and inspect end-to-end business effects.

**Source sections:** `OEBPS/ch12.html#sec_stream_fault_tolerance`, `OEBPS/ch12.html#sec_stream_atomic_commit`, `OEBPS/ch12.html#sec_stream_state_fault_tolerance`, `OEBPS/ch12.html#sec_stream_uses`, `OEBPS/ch12.html#sec_stream_ivm`, `OEBPS/ch12.html#id339`.
