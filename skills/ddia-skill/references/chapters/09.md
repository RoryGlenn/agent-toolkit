# Chapter 9. The Trouble with Distributed Systems

Original applied guidance, not copied book text. These procedures are engineering deductions; retrieve the cited source sections before attributing a consequential claim to DDIA. Verify product/version guarantees independently.

## Source orientation

- Partial failures are nondeterministic: a missing reply may mean a request was lost, delayed, not handled yet, completed with a lost reply, or completed with a delayed reply. A timeout is suspicion, not proof of failure.
- TCP orders and deduplicates bytes within a connection; transport acknowledgment does not establish application processing. Reconnection and request retries require application-level handling.
- Timeout length trades fault-detection delay against false positives and cascading load from premature failover. Network delays, process pauses, overload, and gray failures invalidate fixed timing assumptions.
- Use monotonic clocks for local elapsed durations. Wall-clock timestamps may jump or disagree; high resolution is not accuracy, and last-write-wins based on physical timestamps can discard causally later writes. Bounded-clock schemes depend on correctly maintained uncertainty bounds.
- A lease can expire while its holder pauses or its request is in flight. Correctness requires the protected resource to reject old fencing tokens or enforce suitable atomic conditional writes. A newly granted token must reach the resource before old holders are fenced out.
- Define the system model and separate safety, which must hold despite allowed failures, from liveness, whose eventual progress depends on recovery assumptions. Proofs and models are useful but must be paired with implementation testing; deterministic simulation requires controlling all nondeterminism.

## Networks, partial failure and timeouts

Concept: `ambiguous-failure`.

**Apply when:** A remote call fails or a node is declared dead.

**Procedure:** Enumerate request lost, process paused, effect committed/response lost and asymmetric reachability. Trace queues and caller deadlines. Define retry/identity and unknown-outcome handling based on business consequences.

**Qualifications:** TCP delivery/order does not prove remote application commit. A timeout is suspicion, not knowledge that an operation did not happen.

**Incorrect example:** Treat every timeout as a failed operation and immediately issue a new irreversible request.

**Sufficient example:** Use stable intent identity and query/reconciliation for ambiguity, with bounded load-aware retries.

**Falsification check:** Inject lost responses, one-way partitions and pauses; observe actual effects and eventual operator state.

**Source sections:** `OEBPS/ch09.html#sec_distributed_partial_failure`, `OEBPS/ch09.html#sec_distributed_tcp`, `OEBPS/ch09.html#sec_distributed_queueing`.

## Wall time, monotonic clocks and uncertainty

Concept: `clock-assumptions`.

**Apply when:** Use timestamps for deadlines, ordering, ownership or conflict resolution.

**Procedure:** Classify elapsed duration versus calendar time and causality. Use monotonic time for local elapsed durations; explicitly account for synchronization uncertainty and process pauses where real-time reasoning matters. Inspect platform guarantees.

**Qualifications:** A monotonic clock is local, not a globally comparable timestamp. NTP synchronization does not eliminate uncertainty or backward wall-time adjustments.

**Incorrect example:** Expire an exclusive claim using a wall clock that can move backward, then rely on it for cross-node correctness.

**Sufficient example:** Keep elapsed timers local and use an ownership protocol with validated ordering/fencing for correctness.

**Falsification check:** Step wall time, pause a worker and reorder operations; verify deadlines and resource access under the stated model.

**Source sections:** `OEBPS/ch09.html#sec_distributed_monotonic_timeofday`, `OEBPS/ch09.html#sec_distributed_clocks_relying`.

## Leases, pauses and resource-enforced fencing

Concept: `leases-fencing`.

**Apply when:** A distributed lock protects writes or worker ownership.

**Procedure:** Trace acquisition, lease expiry, paused owner resumption and delayed requests. Ensure monotonically ordered fencing/ownership tokens are checked at the protected resource atomically with writes. Distinguish liveness optimization from correctness.

**Qualifications:** The lock service cannot stop an old worker from issuing I/O. Fencing only works if every relevant write boundary rejects stale tokens.

**Incorrect example:** Check lease validity, pause, then write after a new owner has committed.

**Sufficient example:** Have the protected resource reject a stale ownership token even if the old client resumes.

**Falsification check:** Pause owner A, let B acquire and write, then deliver A delayed write; verify rejection at the resource.

**Source sections:** `OEBPS/ch09.html#sec_distributed_lock_fencing`, `OEBPS/ch09.html#sec_distributed_fencing_tokens`.

## Safety, liveness and Byzantine assumptions

Concept: `failure-models`.

**Apply when:** Claim an algorithm tolerates faults or always makes progress.

**Procedure:** State the safety property, progress conditions, timing/network model, fault count and trust assumptions. Separate accidental corruption, crash faults and malicious participants. Check deployment behavior against modeled assumptions.

**Qualifications:** A proof is conditional on its model. Safety can hold while progress stops; Byzantine tolerance may be unnecessary for a trusted crash-fault setting.

**Incorrect example:** Promise progress during arbitrary permanent partition because a consensus implementation was selected.

**Sufficient example:** State the quorum/connectivity conditions for progress and the invariant maintained while unavailable.

**Falsification check:** Partition or pause enough participants to stop progress and verify safety remains; separately test recovery when conditions return.

**Source sections:** `OEBPS/ch09.html#sec_distributed_byzantine`, `OEBPS/ch09.html#sec_distributed_system_model`, `OEBPS/ch09.html#sec_distributed_safety_liveness`.

## Formal models, fault injection and deterministic simulation

Concept: `formal-testing`.

**Apply when:** Validate a protocol with many schedules or rare failure windows.

**Procedure:** Specify state transitions and invariants, then use bounded model checking or property/fault tests suited to the claim. Preserve failing schedules/seeds. For deterministic simulation control clocks, network, I/O and scheduling rather than merely seeding random test order.

**Qualifications:** A bounded model proof is not a production-code proof. Seeded randomized ordering alone does not establish deterministic replay of a real system.

**Incorrect example:** Run one seeded stress test and report that all possible races have been proven absent.

**Sufficient example:** Report explored bounds and observable code coverage; replay counterexamples and complement model tests with actual-engine checks.

**Falsification check:** Replay a failing schedule exactly, vary bounds, and deliberately introduce a known violation to establish the oracle detects it.

**Source sections:** `OEBPS/ch09.html#sec_distributed_formal`, `OEBPS/ch09.html#id257`, `OEBPS/ch09.html#sec_deterministic_simulation_testing`.
