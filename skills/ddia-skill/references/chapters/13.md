# Chapter 13. A Philosophy of Streaming Systems

Original applied guidance, not copied book text. These procedures are engineering deductions; retrieve the cited source sections before attributing a consequential claim to DDIA. Verify product/version guarantees independently.

## Source orientation

- This chapter explicitly presents an opinionated streaming philosophy. Designate systems of record and deterministic derived views, and make write ordering and provenance explicit. If one integrated product satisfies the need, prefer it over composing additional infrastructure.
- Asynchronous derivation can contain component failures and support independent teams, but consumes retention/catch-up capacity and provides weaker default timeliness. Total ordering across shards, regions, services, and offline clients is not automatic.
- Reprocessing allows old/new derived representations to coexist and enables gradual reversible migration. Reproducibility requires stable inputs, deterministic processing, meaningful event-time handling, and fault semantics.
- Correctness must be end-to-end: transport deduplication and database transactions do not suppress repeated user requests across reconnects. Pass a stable request identity to the durable effect and enforce uniqueness atomically.
- Integrity and timeliness are distinct. Ordered deterministic processing with deduplication can preserve eventual multishard effects without synchronous cross-shard atomic commit; it does not provide immediate cross-shard atomic visibility.
- Hard constraints need timely coordination; accepting temporary violations with compensation is a business decision, not an engineering default. Auditability and periodic end-to-end integrity checks detect faults outside idealized assumptions.

## Authoritative-derived DAGs and causal order

Concept: `derived-dag`.

**Apply when:** Compose several specialized data systems.

**Procedure:** Draw the derivation DAG, authoritative inputs, partition keys and causal dependencies. Define failure/lag behavior at every edge and identify cycles or competing authorities. Check whether required cross-partition order is represented.

**Qualifications:** A total order can be expensive and unnecessary; absence of required causal order can break correctness. The philosophy is not a mandate to unbundle databases.

**Incorrect example:** Run bidirectional synchronization between two independently writable authorities with no conflict semantics.

**Sufficient example:** Choose explicit authority and directed derivation; retain a simpler integrated store when it meets the workload.

**Falsification check:** Delay and reorder each edge, rebuild a downstream view and verify required causal dependencies.

**Source sections:** `OEBPS/ch13.html#sec_future_integration`, `OEBPS/ch13.html#sec_future_capture_causality`.

## Reprocessing and batch/stream convergence

Concept: `reprocessing-evolution`.

**Apply when:** Replace derivation logic without stopping live ingestion.

**Procedure:** Pin input/code versions, build the new view from retained history, catch up and compare before cutover. Define convergence, freshness, backfill resource limits and rollback. Check schema and historical reference data.

**Qualifications:** Equal counts are not semantic equivalence. Reprocessing can overload sources or repeat external effects if it targets live business state.

**Incorrect example:** Replay every event through new billing code directly into the existing charge sink.

**Sufficient example:** Build an isolated versioned projection, validate and switch readers; keep irreversible effects outside uncontrolled replay.

**Falsification check:** Compare business aggregates and sampled records while live events arrive; abort and roll back mid-cutover.

**Source sections:** `OEBPS/ch13.html#sec_future_batch_streaming`, `OEBPS/ch13.html#sec_future_reprocessing`.

## Dataflow composition and observing derived state

Concept: `dataflow-clients`.

**Apply when:** Push updates to clients or separate application state and derivation.

**Procedure:** Trace write acknowledgement through views, subscriptions and offline clients. Specify read consistency, access control, invalidation, resubscription and missing-history recovery. Weigh component independence against integration cost.

**Qualifications:** A server-side derived view does not automatically make client state fresh or authorized. Offline clients introduce additional replicas and schema versions.

**Incorrect example:** A disconnected client resumes from an expired offset and silently retains deleted authorized data.

**Sufficient example:** Require resnapshot/reconciliation when history is missing and apply deletion/permission semantics through the client boundary.

**Falsification check:** Disconnect across retention and schema changes; reconnect and verify state, permissions and visible freshness.

**Source sections:** `OEBPS/ch13.html#sec_future_dataflow`, `OEBPS/ch13.html#sec_future_observing`, `OEBPS/ch13.html#id366`.

## Intent identity and end-to-end correctness

Concept: `end-to-end-identity`.

**Apply when:** Suppress duplicate business operations across clients and services.

**Procedure:** Identify the user intent, stable key scope, payload binding, retention and all effects. Reject a reused identity with different payload. Coordinate truly global uniqueness where required; choose explicit pending or compensatable outcomes only with product acceptance.

**Qualifications:** A library retry key or broker message ID may not represent the original user intent. Duplicate suppression at one layer cannot cover unrelated external effects.

**Incorrect example:** Reuse one request ID for two different transfers and return the first success as if the second transfer happened.

**Sufficient example:** Bind identity to the validated transfer payload and return a conflict for reuse with different intent.

**Falsification check:** Retry across client/service restarts, change payload under the same key and count each externally observable effect.

**Source sections:** `OEBPS/ch13.html#sec_future_end_to_end`, `OEBPS/ch13.html#id374`, `OEBPS/ch13.html#sec_future_constraints`.

## Integrity, timeliness and reconciliation

Concept: `integrity-audit`.

**Apply when:** Relax synchronous coordination or trust a data platform promise.

**Procedure:** Separate when a result appears from whether final business facts are correct. State constraints that must hold immediately and those allowed to reconcile. Build independent cross-system checks, provenance and repair that preserve original intent.

**Qualifications:** Eventual integrity is not immediate atomic visibility or strict serializability. Compensation cannot retroactively satisfy every hard constraint.

**Incorrect example:** Allow a prohibited overdraft and call an eventual refund equivalent to never exceeding the limit.

**Sufficient example:** Coordinate the hard admission constraint; permit delayed derived balances only where the product accepts it and can reconcile.

**Falsification check:** Introduce omissions, duplicates and incorrect transformations; verify independent audits detect semantic discrepancies and repair safely.

**Source sections:** `OEBPS/ch13.html#sec_future_integrity`, `OEBPS/ch13.html#sec_future_verification`.
