# Chapter 3. Data Models and Query Languages

Original applied guidance, not copied book text. These procedures are engineering deductions; retrieve the cited source sections before attributing a consequential claim to DDIA. Verify product/version guarantees independently.

## Source orientation

- Choose the model from relationships and query shape: bounded one-to-many aggregates loaded together suit documents; normalized relations suit shared many-to-one and many-to-many data; variable-length traversals can suit graph models and recursive languages. A graph-shaped problem alone does not require a separate graph database, since models can be represented in other engines with different ergonomics.
- Normalization stores a fact once and makes updates easier, at the cost of joins. Denormalization is derived data: extra copies require update logic, space, and consistency after partial failure. At small-to-moderate scale normalized data often reduces implementation burden. At scale, selective denormalization can coexist with ID hydration and joins for rapidly changing fields.
- Document locality helps only when much of the aggregate is read together. Large documents and frequent small changes can waste reads and rewrite work. Unbounded collections such as many thousands of comments are less appropriate to embed as one aggregate.
- Schema-on-read does not eliminate schema: it moves assumptions into every reader. Heterogeneous or externally controlled inputs can justify it; homogeneous records often benefit from explicit validation. Migration cost and mixed historical records still need handling under either model.
- Declarative queries let the optimizer choose execution and can evolve without rewriting procedural algorithms. ORMs can reduce boilerplate, but do not remove schema design and may introduce N+1 requests or awkward generated queries.
- Event sourcing stores validated facts in order, then derives read models. Commands may be rejected before becoming events; projections cannot reject committed facts. Deterministic replay requires preserving external inputs such as exchange rates, and replay must not repeat real-world side effects. Immutable events complicate erasure and require a deletion strategy.
- Analytics may prefer star, snowflake, or denormalized historical tables; DataFrames bridge relational data and sparse/multidimensional numerical representations. The useful representation follows downstream operations, not a universal choice.

## Relations, documents and locality

Concept: `aggregate-models`.

**Apply when:** Choose a record model or ORM representation.

**Procedure:** Map relationship cardinalities, update ownership, aggregate size and access locality. Compare bounded documents with normalized relations for shared many-to-one/many-to-many facts. Inspect actual joins and document rewrite cost.

**Qualifications:** Model and database product are separate choices. Schema-on-read transfers validation/evolution work to readers; it does not remove schemas.

**Incorrect example:** Embed every organization description into every employee document despite frequent shared corrections.

**Sufficient example:** Normalize shared organizations; embed a bounded private address list when loaded and updated together.

**Falsification check:** Change one shared fact and query all dependents; test growing documents, partial updates and missing-field readers.

**Source sections:** `OEBPS/ch03.html#sec_datamodels_history`, `OEBPS/ch03.html#sec_datamodels_document_summary`.

## Denormalization and analytical schemas

Concept: `denormalization`.

**Apply when:** Duplicate data or choose star/snowflake analytics.

**Procedure:** Identify authoritative dimensions, update frequency, join cost and historical interpretation. Specify repair and refresh for duplicated facts. Compare analytics-friendly fact/dimension schemas against the transactional representation.

**Qualifications:** Denormalization creates synchronization obligations. Current dimension values and event-time dimension values answer different questions.

**Incorrect example:** Copy customer region into orders without defining whether reports need current or historical region.

**Sufficient example:** Define event-time region or join a versioned dimension; document refreshing behavior for current-state copies.

**Falsification check:** Correct a dimension, replay the report and verify the intended temporal meaning and repair behavior.

**Source sections:** `OEBPS/ch03.html#sec_datamodels_normalization`, `OEBPS/ch03.html#sec_datamodels_analytics`.

## Graphs, recursive queries and language choice

Concept: `graph-queries`.

**Apply when:** Implement traversal, policy inference or nested API reads.

**Procedure:** Express one representative variable-depth query and bounded alternatives in recursive SQL, property-graph/Cypher, triples/SPARQL or Datalog as relevant. Compare explainability, indexing, cycles and authorization. For GraphQL, inspect resolver fan-out and access rules.

**Qualifications:** Graph-shaped data does not require a graph database. GraphQL is an API query interface, not a storage model or automatic N+1 solution.

**Incorrect example:** Install a graph store for a two-hop relation and expose unrestricted recursive API resolution.

**Sufficient example:** Benchmark recursive SQL first; choose specialized traversal when workload and maintainability justify it, with bounded authorized resolution.

**Falsification check:** Use cycles, high-degree nodes and unauthorized edges; measure query work and returned information.

**Source sections:** `OEBPS/ch03.html#sec_datamodels_graph`, `OEBPS/ch03.html#id62`, `OEBPS/ch03.html#id63`.

## Event sourcing and CQRS

Concept: `event-models`.

**Apply when:** An event log is proposed as authoritative history or reads/writes are separated.

**Procedure:** Distinguish domain intent events from database change records. Define event identities, schema evolution, correction/deletion and projection reconstruction. Compare an ordinary state table plus audit log with full event sourcing.

**Qualifications:** CQRS does not require event sourcing or separate services. Replay may require historical business code and enrichment data.

**Incorrect example:** Adopt event sourcing for basic CRUD but retain neither event versions nor the inputs needed to rebuild projections.

**Sufficient example:** Use conventional state when adequate; if history is authoritative, version events and prove projection rebuilds.

**Falsification check:** Reconstruct from old events after a schema change and verify corrections and replayed effects.

**Source sections:** `OEBPS/ch03.html#sec_datamodels_events`, `OEBPS/ch03.html#sec_datamodels_normalization`.

## DataFrames, matrices and arrays

Concept: `analytical-shapes`.

**Apply when:** Convert business records into analytical or ML data structures.

**Procedure:** Define row/column identity, join keys, ordering, missing values, sparsity and type conversion. Preserve feature lineage and split boundaries. Choose relational operations versus dense/sparse arrays according to computation and memory.

**Qualifications:** Position is not durable business identity. A matrix conversion can erase labels or coerce exact values.

**Incorrect example:** Join labels and features by incidental row order after an independent sort.

**Sufficient example:** Carry explicit entity keys through joins, validate uniqueness, then convert to aligned arrays with recorded schema.

**Falsification check:** Shuffle input order, add missing entities and duplicates, and ensure keyed outputs remain correct.

**Source sections:** `OEBPS/ch03.html#sec_datamodels_dataframes`, `OEBPS/ch03.html#sec_datamodels_analytics`.
