# Chapter 4. Storage and Retrieval

Original applied guidance, not copied book text. These procedures are engineering deductions; retrieve the cited source sections before attributing a consequential claim to DDIA. Verify product/version guarantees independently.

## Source orientation

- Indexes are derived structures trading read efficiency for write cost and storage. Choose them from actual predicates and access order; a concatenated key mainly helps leading-key or matching ordered-prefix queries, while independent range predicates may need a multidimensional strategy.
- LSM storage writes sorted immutable segments and uses background compaction plus a durability log; tombstones propagate deletions. B-trees maintain sorted pages with in-place updates and a write-ahead log or copy-on-write protection. Crash safety depends on the actual log flush and recovery behavior, not just the presence of files.
- LSM versus B-tree preferences are rules of thumb, not universal performance guarantees. Point/range reads, overwrite frequency, value size, compaction, amplification, disk space, and SSD behavior affect results. An empty LSM benchmark can hide later compaction costs; sustained measurements are necessary.
- Compaction strategy exchanges write throughput, read amplification, temporary space, and maintenance latency. Memtable pressure can stall operations. Deleted values may remain in old segments until compaction, so logical deletion and physical erasure differ.
- Clustered, heap-referencing, and covering indexes differ in data locality and duplication. Covering more columns can avoid heap lookups but increases index size and update work. In-memory databases still require an explicit durability method if data loss is unacceptable.
- Columnar storage suits analytical scans over many rows but few columns. Sorting and compression reduce I/O, and compilation or vectorized processing reduces CPU overhead. Bulk/log-structured ingestion makes column updates efficient; materialized aggregates speed repeated queries but narrow query flexibility.
- Inverted indexes support lexical search. Vector embeddings plus flat, IVF, or HNSW indexes support similarity search; approximate methods exchange accuracy for speed. The book supplies concepts rather than proof that a particular modern engine or configuration meets a workload.

## Logs, B-trees and LSM tradeoffs

Concept: `storage-engines`.

**Apply when:** Tune or select a storage engine.

**Procedure:** Measure read/write mix, range scans, value size, working set and durability requirements. Compare WAL/memtable/compaction paths with page updates and cache behavior. Account for read, write and space amplification, including background work.

**Qualifications:** LSM is not always faster for writes or worse for reads; workload, implementation and compaction matter. Memory residence does not prove durable persistence.

**Incorrect example:** Benchmark only ingestion before compaction and declare the engine sustains that rate indefinitely.

**Sufficient example:** Measure steady state including compaction, checkpoints, restart and disk headroom.

**Falsification check:** Run beyond multiple compaction/checkpoint cycles and restart; compare p99 latency, durable records and write amplification.

**Source sections:** `OEBPS/ch04.html#sec_storage_log_structured`, `OEBPS/ch04.html#sec_storage_btree_lsm_comparison`.

## Secondary, multicolumn and covering indexes

Concept: `indexes`.

**Apply when:** A query is slow or a new index is proposed.

**Procedure:** Inspect predicates, equality/range ordering, sort, selectivity, row fetches and write cost using the actual query plan. Compare a suitable composite/covering index with query restructuring. Include update and build impact.

**Qualifications:** An index that exists may not support the actual predicate/order. Covering values enlarge maintenance cost and may change visibility behavior by engine.

**Incorrect example:** Add separate indexes on every column and assume a multi-predicate ordered query is efficient.

**Sufficient example:** Use a workload-appropriate composite index after checking the engine plan and write budget.

**Falsification check:** Run representative selective and unselective queries under concurrent writes; inspect plans and scanned rows.

**Source sections:** `OEBPS/ch04.html#sec_storage_index_multicolumn`, `OEBPS/ch04.html#sec_storage_index_heap`.

## Columnar storage and analytical execution

Concept: `columnar`.

**Apply when:** Optimize scans, aggregations, warehouse layout or materialized views.

**Procedure:** Measure projected columns, compression, sort/partition pruning, batch execution and aggregate reuse. Include refresh cost and freshness of materialized views; compare compilation/vectorization only on relevant execution paths.

**Qualifications:** Row and column stores serve different access patterns. A fast warmed query can conceal full scans and stale derived state.

**Incorrect example:** Move a high-frequency single-row update path into a columnar warehouse solely because one aggregate is fast.

**Sufficient example:** Keep operational writes in a suitable system and derive analytical layout when measured scans warrant it.

**Falsification check:** Test cold/warm scans, selective queries, update/refresh lag and total resource cost.

**Source sections:** `OEBPS/ch04.html#sec_storage_column`, `OEBPS/ch04.html#sec_storage_vectorized`, `OEBPS/ch04.html#sec_storage_materialized_views`.

## Full-text and multidimensional search

Concept: `search-indexes`.

**Apply when:** Text, spatial or multidimensional predicates are required.

**Procedure:** Define language normalization, tokenization, scoring, filter combinations and update/deletion visibility. Compare specialized inverted or spatial indexing with database-native capabilities. Trace source-to-index freshness and reindexing.

**Qualifications:** A text substring match and linguistic full-text relevance are different requirements. Index correctness includes permissions and deletions, not just recall.

**Incorrect example:** Publish a search hit after permission removal because the index is treated as an authorization source.

**Sufficient example:** Use the authoritative permission boundary or an explicitly safe derived policy with bounded exposure; rebuild versioned indexes.

**Falsification check:** Test language variants, stale permissions, deletes and a complete reindex during active updates.

**Source sections:** `OEBPS/ch04.html#sec_storage_multidimensional`, `OEBPS/ch04.html#sec_storage_full_text`.

## Vector embeddings and approximate retrieval

Concept: `vector-search`.

**Apply when:** Select or tune vector search for semantic retrieval.

**Procedure:** Choose a representative judged query set and exact-search baseline. Vary candidate count, index parameters, filters and embedding version; measure recall at k, latency, memory, build and update costs. Check tenant/permission filtering before disclosure.

**Qualifications:** Nearest embeddings are not factual truth. ANN sacrifices recall; filtered performance and embedding drift can differ from unfiltered benchmarks.

**Incorrect example:** Choose HNSW by an unfiltered speed demo and assume every authorized relevant result is retrieved.

**Sufficient example:** Compare exact/flat search and approximate configurations on representative filtered queries and a versioned embedding corpus.

**Falsification check:** Measure missed known neighbors, filtered recall, update visibility and full rebuild costs.

**Source sections:** `OEBPS/ch04.html#id94`, `OEBPS/ch04.html#sec_storage_full_text`.
