# Chapter 5. Encoding and Evolution

Original applied guidance, not copied book text. These procedures are engineering deductions; retrieve the cited source sections before attributing a consequential claim to DDIA. Verify product/version guarantees independently.

## Source orientation

- Rolling deployments, delayed client updates, and old stored records produce mixed-version communication. Backward compatibility means new readers can read old writers; forward compatibility means old readers can read new writers. An older read-modify-write path can silently erase newer unknown fields even if parsing succeeds.
- Encoding is a durable contract. Language-native object serialization can couple data to language/classes, offer poor version evolution, and expose unsafe deserialization. JSON/XML/CSV are broadly interoperable but require explicit handling of number precision, bytes, schema and escaping.
- Protobuf identifies fields with stable tags that must not be recycled. Avro resolves a writer schema against a reader schema; writer-schema identity must remain available. Defaults, aliases, union branches, and type changes have direction-specific compatibility constraints. Exact current rules need the specific library/specification.
- Database data can outlive several application generations. A code rollout does not migrate historical rows automatically. Large rewrites, archives, and changes to representation require compatibility across both recent and old records, and sometimes separately versioned formats.
- A remote call has an outcome absent from a local call: timeout with unknown completion. Retry may duplicate an effect unless the protocol supplies deduplication/idempotence. Discovery and balancing solve routing and availability concerns, not that semantic uncertainty.
- Durable workflows retain completed results to replay orchestration, but external APIs still need idempotence and unique IDs. Workflow changes must preserve replay expectations or use separately versioned executions; randomness, clocks and reordered calls can violate determinism.
- Asynchronous brokers provide buffering and decoupling with implementation-specific delivery, retention, and durability. Queue distribution and publish/subscribe differ. Re-emitting consumers must preserve compatibility and unknown fields when required; actor messaging also retains distributed failure and evolution concerns.

## Writer-reader compatibility and rolling evolution

Concept: `compatibility`.

**Apply when:** Deploy mixed versions, change a field or replay archived data.

**Procedure:** Build a matrix of old/new writers and readers including rollback, archived records and old read-modify-write code. Check defaults, unknown fields, missing/null semantics and required field transitions. Use expand/migrate/contract when necessary.

**Qualifications:** Backward and forward compatibility describe different directions. An old client may erase unknown data while rewriting a record.

**Incorrect example:** Rename a required field and deploy readers before old writers stop producing the old shape.

**Sufficient example:** Accept both forms, deploy compatible writers, backfill and verify old-reader retirement before contraction.

**Falsification check:** Exercise all writer-reader pairs plus old-client rewrite, old archive read and rollback.

**Source sections:** `OEBPS/ch05.html#sec_encoding_dataflow_db`, `OEBPS/ch05.html#id110`, `OEBPS/ch05.html#id111`.

## Encoding formats and numeric fidelity

Concept: `encoding-types`.

**Apply when:** Exchange data across languages or deserialize untrusted input.

**Procedure:** Specify exact integer/decimal ranges, bytes, timestamps and nullability; round-trip boundary values through every participating language. Avoid unsafe native object deserialization for untrusted data. Compare schema validation and binary format needs.

**Qualifications:** JSON number syntax does not ensure all implementations preserve 64-bit identity. Binary encoding alone does not provide schema compatibility or security.

**Incorrect example:** Send a 64-bit account ID as a JSON number to a consumer using floating-point numbers.

**Sufficient example:** Use a precisely specified lossless representation and validate it at boundaries.

**Falsification check:** Round-trip adjacent large integers, decimals, binary data, unknown fields and malformed records through actual clients.

**Source sections:** `OEBPS/ch05.html#id98`, `OEBPS/ch05.html#sec_encoding_json`.

## Protocol Buffers and Avro evolution

Concept: `schema-formats`.

**Apply when:** Change a schema-driven binary message.

**Procedure:** Check field-number identity and reservations for Protocol Buffers; retain Avro writer schema identity and valid reader resolution. Review defaults, unions and type promotions using actual tools. Keep historical schemas reachable for old data.

**Qualifications:** Reusing a deleted tag can silently reinterpret bytes. Avro decoding depends on writer schema, not only the latest schema.

**Incorrect example:** Reuse a removed field tag for a different meaning and discard old writer schemas after deployment.

**Sufficient example:** Reserve old tags and retain versioned writer schemas; verify reader resolution for archived payloads.

**Falsification check:** Decode recorded old/new messages with supported readers and test tag reuse or missing-schema failure explicitly.

**Source sections:** `OEBPS/ch05.html#sec_encoding_protobuf`, `OEBPS/ch05.html#sec_encoding_avro`.

## RPC, services and ambiguous outcomes

Concept: `rpc-outcomes`.

**Apply when:** Retry a service request, change an API or add routing middleware.

**Procedure:** Trace request acceptance, commit, response and client timeout. Distinguish unavailable from unknown outcome; bind stable request identity to intended payload where retries must not duplicate effects. Confirm retention, query/reconciliation and version compatibility.

**Qualifications:** A transport acknowledgement is not business completion. REST/RPC/service meshes do not determine effect semantics.

**Incorrect example:** Blindly retry a timed-out charge with a fresh request ID.

**Sufficient example:** Reuse a stable intent identity with provider-supported guarantees, and reconcile unresolved outcomes before another charge.

**Falsification check:** Simulate provider commit followed by lost response, retry and process restart; count observed business effects.

**Source sections:** `OEBPS/ch05.html#sec_problems_with_rpc`, `OEBPS/ch05.html#sec_encoding_dataflow_rpc`.

## Durable workflows and event-driven contracts

Concept: `durable-workflows`.

**Apply when:** Introduce long-running orchestration or change in-flight workflow code.

**Procedure:** Identify durable state, deterministic replay boundary, activity identities and code-version strategy. Check timers, nondeterminism, event schemas and external activities. Compare ordinary jobs when durable coordination is unnecessary.

**Qualifications:** Durable replay does not automatically make external effects exactly once. Product-specific replay/versioning rules require current official documentation.

**Incorrect example:** Replay a workflow containing an unrecorded random branch and repeat a completed external activity.

**Sufficient example:** Record workflow decisions and version changes appropriately; make activities safely identifiable or reconcilable.

**Falsification check:** Replay saved histories across deployment, pause between activity commit and completion recording, and verify external effects.

**Source sections:** `OEBPS/ch05.html#sec_encoding_dataflow_workflows`, `OEBPS/ch05.html#sec_encoding_dataflow_msg`.
