# Chapter 7. Sharding

Original applied guidance, not copied book text. These procedures are engineering deductions; retrieve the cited source sections before attributing a consequential claim to DDIA. Verify product/version guarantees independently.

## Source orientation

- Sharding primarily addresses data volume/write load beyond a node; replication can address read throughput or availability independently. Sharding is often unnecessary for a small workload, because placement choices, cross-shard transactions and secondary-index queries introduce costs.
- A useful partition key balances data and work while keeping required access and invariants local. Uniform distribution of keys does not ensure uniform load. A single hot key remains a hot key under hashing; splitting its writes adds aggregation and bookkeeping to reads.
- Range partitioning supports efficient range scans but can concentrate new monotonic timestamp writes. Hash partitioning spreads nearby keys but loses global range locality. Composite keys can hash or partition a prefix and order records within that partition.
- Hash modulo the current node count causes extensive movement when membership changes. Separate stable logical shards from physical nodes, use adaptive ranges, or a suitable consistent-hash scheme. Fixed shard counts make transfers cheaper but can impose later expensive resharding; too many tiny shards add overhead.
- Tenant shards can isolate resources, permissions, faults, restore operations and residency, but require a strategy for unusually large tenants, many small tenants, cross-tenant queries and tenant movement. Physical separation helps but is not a complete security guarantee.
- Splitting and rebalancing consume disk/network/CPU and must coexist with writes. Automated failure detection and rebalancing can amplify overload into cascading failures. Routing must handle authoritative assignments, changes, split-brain coordinators, and in-flight requests during cutover.
- Local secondary indexes make writes local but queries without the partition key scatter to every shard, amplifying tails and limiting throughput scaling. Global indexes speed term lookup but distribute index updates, may require coordination, and can be stale when asynchronous. Fetching records or intersecting large postings lists can still involve many shards.

## Sharding need and multitenancy

Concept: `sharding-need`.

**Apply when:** Split data across nodes or isolate tenants.

**Procedure:** Measure storage/write/query capacity and tenant distribution independently from read replication. Compare vertical growth, indexing, tenant isolation and sharding. Include multi-shard transactions and operator cost.

**Qualifications:** Sharding and replication solve different resource/fault problems. Tenant-per-shard may fail for both very small and extremely large tenants.

**Incorrect example:** Shard merely because replicas exist, using average tenant size to plan capacity.

**Sufficient example:** Identify the actual constrained resource and accommodate dominant tenants explicitly.

**Falsification check:** Load the largest tenant and many small tenants; compare capacity and noisy-neighbor effects.

**Source sections:** `OEBPS/ch07.html#sec_sharding_reasons`, `OEBPS/ch07.html#sec_sharding_multitenancy`.

## Range, hash and composite keys

Concept: `shard-keys`.

**Apply when:** Choose a partition key.

**Procedure:** List point/range access, join locality, key distribution and time trends. Compare range/hash/composite keys and query fan-out. Check whether monotonic writes or one hot entity concentrate work.

**Qualifications:** Hashing spreads different keys; it does not split a single hot key. Range locality trades against hotspot risk.

**Incorrect example:** Partition append-only traffic by current timestamp and expect balanced writes.

**Sufficient example:** Choose an intentional spread/locality tradeoff, such as time buckets with a suitable hash component.

**Falsification check:** Replay skewed and monotonic workloads; measure busiest-shard work and query fan-out.

**Source sections:** `OEBPS/ch07.html#sec_sharding_key_range`, `OEBPS/ch07.html#sec_sharding_hash`.

## Hot keys and secondary effects

Concept: `hotspots`.

**Apply when:** One partition saturates despite spare cluster capacity.

**Procedure:** Identify key-level service demand, large values, celebrity fan-out and index updates. Compare splitting state, salting, caching or bounded aggregation with the read/reassembly and invariant cost each adds.

**Qualifications:** More nodes cannot fix a non-splittable serial bottleneck. Salting changes reads and ordering semantics.

**Incorrect example:** Add ten nodes to a cluster whose one counter receives most writes.

**Sufficient example:** Reduce or partition that operation only if semantics permit; otherwise size and bound the authoritative hotspot.

**Falsification check:** Send a single dominant key alongside uniform traffic and inspect per-key latency and correctness.

**Source sections:** `OEBPS/ch07.html#sec_sharding_skew`, `OEBPS/ch07.html#sec_sharding_secondary_indexes`.

## Rebalancing and routing

Concept: `rebalancing`.

**Apply when:** Add nodes, move shards or change routing.

**Procedure:** Prefer stable logical partitions or deliberate range movement over naive modulo remapping. Define copy/catch-up/cutover ownership, forwarding, stale routes, headroom and rollback. Protect concurrent writes across the ownership transition.

**Qualifications:** Automatic rebalancing still consumes network, I/O and replicas. Routing discovery is not proof that only one owner accepts writes.

**Incorrect example:** Change hash(key)%node_count and immediately point clients at new empty shards.

**Sufficient example:** Transfer stable partitions with explicit versioned ownership and a tested read/write transition.

**Falsification check:** Move a hot shard during writes, crash before/after cutover and send requests using stale routes.

**Source sections:** `OEBPS/ch07.html#id164`, `OEBPS/ch07.html#sec_sharding_operations`, `OEBPS/ch07.html#sec_sharding_routing`.

## Local and global secondary indexes

Concept: `distributed-indexes`.

**Apply when:** Query sharded data by a non-partition key.

**Procedure:** Trace where index entries live and who updates them atomically. Compare local indexes plus scatter/gather with globally partitioned indexes, update fan-out, freshness and cross-shard constraints.

**Qualifications:** A global lookup can add a second distributed consistency boundary. Local index existence does not eliminate scatter/gather.

**Incorrect example:** Advertise unique email across shards using only per-shard unique indexes.

**Sufficient example:** Coordinate the required global uniqueness or redesign ownership; choose lookup indexing separately from admission.

**Falsification check:** Write duplicate indexed keys on different shards and fail between data/index updates; check the specified constraint.

**Source sections:** `OEBPS/ch07.html#id171`, `OEBPS/ch07.html#id172`.
