# Chapter 11. Batch Processing

Original applied guidance, not copied book text. These procedures are engineering deductions; retrieve the cited source sections before attributing a consequential claim to DDIA. Verify product/version guarantees independently.

## Source orientation

- Batch jobs transform bounded immutable inputs into regenerable outputs. Avoiding external side effects allows retries, version rollback, auditing, and recovery from faulty transformation code. Throughput and completion time often matter more than per-record latency.
- A local pipeline can process substantial data. Hash aggregation memory depends on distinct-key cardinality, while external sorting can spill and merge sequentially. Distribution is justified by actual capacity or time requirements, not input volume slogans.
- Distributed filesystems, object stores, and local filesystems differ in rename, locking, append, consistency, and locality semantics even when interfaces appear compatible. Storage/compute separation trades network movement against independent scaling.
- Job scheduling allocates resources among tasks; workflow scheduling manages inter-job dependencies. Task retries, preemption, recomputation, and checkpoints have different storage/compute and recovery costs.
- Shuffle brings equal-key data together for joins and grouping. High-level query/DataFrame plans enable optimization, but distributed ordering/index semantics can differ from local APIs.
- Writing per-row side effects to production from a batch task can overwhelm the service and expose partial or duplicate output. Stream buffering does not itself provide all-or-nothing publication; versioned bulk output or an explicit completion/publication protocol is required.

## Local pipelines, sorting and memory bounds

Concept: `batch-baseline`.

**Apply when:** Choose a batch framework or process a large file.

**Procedure:** Specify bounded input size, cardinality, memory, sort/order and repeatability. Compare Unix/SQL/DataFrame/local external sort with distributed execution. Account for hash aggregation growth and skew, not only input byte size.

**Qualifications:** A streaming reader can still retain unbounded aggregate state. Distribution adds data movement and operation cost.

**Incorrect example:** Use a cluster for a daily 50MB file, or call a dict aggregation constant-memory because input is streamed.

**Sufficient example:** Use a bounded local pipeline when sufficient; spill/sort when key cardinality exceeds memory.

**Falsification check:** Increase unique-key cardinality under a memory limit and compare exact outputs with a small trusted reference.

**Source sections:** `OEBPS/ch11.html#sec_batch_unix`, `OEBPS/ch11.html#id292`.

## Filesystems, object stores and reproducible inputs

Concept: `batch-storage`.

**Apply when:** Run jobs over remote files or object storage.

**Procedure:** Pin input manifests, object versions, schema and transformation code. Inspect list/read/rename/commit semantics for the actual store. Plan locality, transfer cost and handling of partially published inputs.

**Qualifications:** An object-store prefix is not necessarily an atomic directory snapshot. Product behavior must be verified, not inferred from filesystem APIs.

**Incorrect example:** List a changing prefix while processing and later claim the run can be reproduced exactly.

**Sufficient example:** Capture a versioned input manifest and publish complete outputs through a defined commit marker/pointer.

**Falsification check:** Mutate inputs during planning/execution and prove the selected version set is stable and auditable.

**Source sections:** `OEBPS/ch11.html#sec_batch_dfs`, `OEBPS/ch11.html#id295`.

## Resource scheduling, dependencies and retries

Concept: `batch-orchestration`.

**Apply when:** Schedule dependent jobs, checkpoints or retries.

**Procedure:** Separate resource placement from workflow dependency completion. Define task identity, stable inputs, speculative/retry behavior, checkpoints and idempotent publication. Bound retries and downstream load.

**Qualifications:** A scheduler task success is not proof that externally visible outputs are complete or unique. Retrying a task may repeat effects.

**Incorrect example:** Append output on every retry and mark the whole partition complete after only the first file arrives.

**Sufficient example:** Write attempt-local outputs and commit one complete version with observable reconciliation.

**Falsification check:** Kill attempts before and after output publication; ensure readers see a complete selected result and no repeated business effects.

**Source sections:** `OEBPS/ch11.html#id296`, `OEBPS/ch11.html#sec_batch_workflows`, `OEBPS/ch11.html#id299`.

## Shuffles, joins, grouping and skew

Concept: `batch-dataflow`.

**Apply when:** Choose distributed join/grouping strategy.

**Procedure:** Measure key distribution, input sizes, partition alignment and available memory. Compare broadcast, hash and sort-merge approaches; account for network shuffle, heavy keys and spill. Validate duplicate/null and join cardinality semantics.

**Qualifications:** Equal partition counts do not prove co-partitioning. A small average group hides an unbounded hot group.

**Incorrect example:** Broadcast a dimension whose production size exceeds every worker memory limit.

**Sufficient example:** Use measured broadcast bounds or a partitioned/spilling join with skew handling.

**Falsification check:** Run skewed joins with duplicates and nulls; compare counts and checksums against a trusted exact query.

**Source sections:** `OEBPS/ch11.html#sec_batch_dataflow`, `OEBPS/ch11.html#sec_shuffle`, `OEBPS/ch11.html#sec_batch_join`.

## ETL, ML and serving complete derived output

Concept: `derived-publication`.

**Apply when:** Publish reports, features, indexes or models from batch results.

**Procedure:** Define output schema, lineage, input/code versions, validation thresholds and downstream capacity. Validate before atomically selecting a complete version. Keep the prior version for rollback; separate training and evaluation data.

**Qualifications:** A successful computation is not a successful serving rollout. A single checksum does not validate semantic correctness or prevent leakage.

**Incorrect example:** Replace a live index file by file, exposing a mixture of old and new partitions.

**Sufficient example:** Build a versioned complete output, validate it and switch an authoritative pointer with rollback.

**Falsification check:** Interrupt publication, query during cutover and compare business aggregates plus version consistency.

**Source sections:** `OEBPS/ch11.html#sec_batch_output`, `OEBPS/ch11.html#id308`, `OEBPS/ch11.html#sec_batch_serving_derived`.
