# Chapter 8. Transactions

Original applied guidance, not copied book text. These procedures are engineering deductions; retrieve the cited source sections before attributing a consequential claim to DDIA. Verify product/version guarantees independently.

## Source orientation

- Transactions are a programming abstraction that reduce specified partial-failure and concurrency cases to commit or abort. Decide using the application invariant and actual guarantee, rather than an ACID marketing label. Atomicity is abortability; isolation concerns concurrent interference; application logic or declared constraints must preserve consistency.
- Read committed prevents dirty reads/writes but permits read skew and lost updates. Snapshot isolation provides a consistent snapshot but permits write skew, and implementations differ in lost-update detection. True serializability protects cross-object decision predicates; a single-object atomic operation protects only its own scope.
- Prefer an atomic database update when it expresses the operation. Otherwise compare locking, conditional writes with checked outcomes, and serializable transactions plus whole-transaction retry. SELECT FOR UPDATE locks returned rows and cannot by itself protect an empty result from a phantom insert.
- Keep read/write transactions short. Pessimistic 2PL may block readers and writers, deadlock, and create tail latency; SSI can reduce blocking but must detect conflicts and abort/retry, with contention and long transactions increasing retry cost. Serial execution works when transactions are short and local to a shard.
- 2PC coordinates atomic commit across participants and is distinct from 2PL isolation. Prepared participants cannot unilaterally abort after promising to commit; coordinator loss leaves in-doubt transactions holding locks. Internal distributed transactions with replicated coordinators differ materially from heterogeneous XA integration.
- Exactly-once database effects can use a unique message ID recorded in the same transaction as the effect, followed by broker acknowledgment. Transaction retries do not automatically deduplicate an uncertain prior commit, nor undo external side effects.

## ACID meanings and multi-object atomicity

Concept: `transaction-boundaries`.

**Apply when:** Define a transaction boundary or infer guarantees from ACID.

**Procedure:** Map the business operation to exact records and commit boundaries. Separate atomicity, isolation, durability and invariant enforcement; inspect constraint and transaction configuration. Include error handling and rollback of all relevant objects.

**Qualifications:** Single-record atomicity does not imply multi-record isolation. Consistency in ACID does not mean replica consistency or automatic business correctness.

**Incorrect example:** Debit one account and credit another in independent commits, calling each ACID update a transfer.

**Sufficient example:** Commit the required database effects together or explicitly define a recoverable multi-step business protocol.

**Falsification check:** Fail after each mutation and observe whether the business invariant survives rollback and restart.

**Source sections:** `OEBPS/ch08.html#sec_transactions_acid`, `OEBPS/ch08.html#sec_transactions_multi_object`.

## Read committed, snapshots and lost updates

Concept: `isolation-anomalies`.

**Apply when:** Code reads then writes shared state.

**Procedure:** Trace dirty reads/writes, inconsistent reads and concurrent read-modify-write. Inspect actual engine/isolation behavior. Compare conditional atomic updates, compare-and-set, row locks and transaction retries; check affected-row counts.

Distinguish the anomalies with an explicit operation history; do not treat every race
as a lost update:

| Anomaly | Counterexample to construct | Candidate protection to verify |
| --- | --- | --- |
| Dirty read | B observes A's new value; A aborts. | Reads exclude other uncommitted writes. |
| Dirty write | Two uncommitted transactions overwrite one another's related changes. | Write locking/conflict handling protects uncommitted changes. |
| Read skew | Read one side of a transfer before commit and the other side afterward. | A sufficiently scoped consistent snapshot for the required observation. |
| Lost update | A and B read ten; both write eleven despite two accepted increments. | Atomic increment, checked CAS or correctly held row lock. |
| Write skew | A and B read a shared predicate; disjoint writes make it false. | Suitable constraint/materialized conflict or serializability with whole-transaction retries. |
| Phantom | Two transactions observe no overlapping booking, then insert overlapping rows. | An appropriate declarative constraint or predicate/range protection; locking an empty result is insufficient. |

Run the history on the intended engine and isolation setting. Test rollback as well as
successful concurrency. If a transaction must retry, recompute its reads and decisions;
do not blindly repeat external effects that may already have succeeded.

**Qualifications:** Isolation names vary by engine. A transaction wrapper alone does not prevent a lost update, and lock scope matters.

**Incorrect example:** Two workers read capacity one and both later write zero after admitting different customers.

**Sufficient example:** Use an atomic conditional decrement plus the related admission write in the same transaction.

**Falsification check:** Force both reads before either write; verify successful admissions never exceed capacity and failed transactions restore it.

**Source sections:** `OEBPS/ch08.html#sec_transactions_snapshot_isolation`, `OEBPS/ch08.html#sec_transactions_lost_update`, `OEBPS/ch08.html#sec_transactions_read_committed`, `OEBPS/ch08.html#id187`, `OEBPS/ch08.html#sec_transactions_dirty_write`.

## Predicate invariants and serializability

Concept: `write-skew`.

**Apply when:** An invariant depends on a set of rows or absence of rows.

**Procedure:** Construct two transactions whose disjoint writes invalidate a shared predicate. Compare constraint materialization, predicate/range locking, serial execution or SSI with retries. Verify the engine and access path protect the predicate, including empty sets.

Compare serializable strategies against transaction shape. Actual serial execution can
work well for short, local transactions but long interactive/network waits reduce useful
capacity. Two-phase locking may protect rows and predicate/index ranges while introducing
blocking, deadlock and tail latency. Serializable snapshot isolation tracks dependencies
and may abort one transaction instead of blocking it; validate contention/retry behavior.
These are mechanisms to evaluate, not equivalent configuration switches across products.

**Qualifications:** Snapshot isolation can permit write skew. Locking existing rows does not automatically protect a predicate with no matching rows.

**Incorrect example:** Two doctors each see the other on call and independently go off call under snapshot isolation.

**Sufficient example:** Protect the shared invariant using a supported serializable transaction/retry or an appropriate materialized constraint.

**Falsification check:** Run the critical interleaving against the intended engine; force serialization failures and verify whole-transaction retry behavior.

**Source sections:** `OEBPS/ch08.html#sec_transactions_write_skew`, `OEBPS/ch08.html#sec_transactions_phantom`, `OEBPS/ch08.html#sec_transactions_ssi`, `OEBPS/ch08.html#sec_transactions_serial`, `OEBPS/ch08.html#sec_transactions_2pl`, `OEBPS/ch08.html#sec_transactions_2pl_predicate`, `OEBPS/ch08.html#sec_transactions_2pl_range`.

## Atomic commit and coordinator recovery

Concept: `distributed-transactions`.

**Apply when:** A business operation spans transaction participants.

**Procedure:** Identify participants, coordinator decision log, prepare locks and recovery protocol. Distinguish DB-internal distributed commit from XA integration. Evaluate availability of in-doubt transactions and compare explicit application coordination when appropriate.

**Qualifications:** Two-phase locking provides isolation; two-phase commit provides atomic decision. Neither name alone promises nonblocking operation or end-to-end external effects.

**Incorrect example:** Release prepared locks on a timeout while the coordinator may already have committed elsewhere.

**Sufficient example:** Recover the durable transaction decision according to the protocol, with operational handling for in-doubt participants.

**Falsification check:** Crash coordinator/participants at prepare and decision boundaries; verify agreement and recovery without unilateral guesses.

**Source sections:** `OEBPS/ch08.html#sec_transactions_2pc`, `OEBPS/ch08.html#sec_transactions_xa`, `OEBPS/ch08.html#sec_transactions_internal`.

## Message identity, effect, acknowledgement and retention

Concept: `message-atomicity`.

**Apply when:** Process redelivered messages or clean deduplication records.

**Procedure:** Bind stable business/message identity to payload; atomically commit database effect and marker before acknowledgement. Define actual replay, retry and in-flight horizons before cleanup. Trace external effects separately from the local transaction.

**Qualifications:** Deleting IDs after ack assumes no later delivery or operational replay. Local dedupe cannot alone make a remote side effect exactly once.

**Incorrect example:** Delete processed identities after acknowledgement, then replay old log entries into the same business state.

**Sufficient example:** Retain identities for the real horizon or enforce durable business uniqueness; make replay target/state explicit.

**Falsification check:** Crash before commit and after commit/before ack, redeliver concurrently, replay after cleanup and check counted effects.

**Source sections:** `OEBPS/ch08.html#sec_transactions_exactly_once`, `OEBPS/ch08.html#id225`.
